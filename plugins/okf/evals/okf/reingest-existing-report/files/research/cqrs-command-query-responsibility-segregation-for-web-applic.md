# CQRS (Command Query Responsibility Segregation) for web applications: how it works, strengths, weaknesses, when to use it, when not to use it, trade-offs versus alternative patterns, and real-world examples in 2025-2026 practice

> Generated by /ae-research → research on 2026-11-15

## Summary
CQRS splits one conceptual model into separate models for commands (writes) and queries (reads). It does not require separate databases, event sourcing or a message bus; those are optional ways to implement it. The canonical guidance from Fowler, Microsoft, Young and Dahan is to apply CQRS only within specific bounded contexts that benefit from it. Collaborative or read-heavy domains are the best candidates. Simple CRUD domains, and most bounded contexts in a typical system, should not use it. The main benefit is that each side can be optimized and scaled on its own. The main cost is complexity, and once the stores are split, eventual consistency: stale reads hurt the user experience, and the write and read sides have to be kept in sync reliably. Netflix Tudum (2025) shows both sides of this. Its Kafka/Cassandra CQRS read path left editors waiting minutes for previews. Netflix kept CQRS but replaced that read path with an in-memory store, RAW Hollow, that can give strong consistency per request, and page build time fell from about 1.4s to 0.4s.

## Findings
- **CQRS means using separate models for updates (commands) and reads (queries) where there used to be one model. The pattern is about separating models and code paths. It is not about database topology: it works with one database or many, and needs no particular storage technology.** — confidence: high
  - Evidence: Fowler: 'split that conceptual model into separate models for update and display.' Microsoft's CQRS Journey: CQRS 'does not mandate that you split the data store, or that you use any particular persistence technology... relational database, NoSQL store, or event store'. It describes CQRS as a pattern that facilitates splitting the store. Comartin (2026): 'Commands change state. Queries read state. That has nothing to do with databases. One database, two databases.' Fowler also says both models can share one database. Votes were 3-0 on all merged claims (0, 4, 20).
  - Sources: https://www.martinfowler.com/bliki/CQRS.html, https://learn.microsoft.com/en-us/previous-versions/msp-n-p/jj591573(v=pandp.10), https://codeopinion.com/read-replicas-are-not-cqrs-stop-confusing-this/
- **Read replicas (one write primary plus replica databases for reads) are a scaling technique, not CQRS. The replicas copy the same schema and model, so nothing is split. A replica can be one way to physically host a CQRS read side, but that does not make the two the same thing.** — confidence: medium
  - Evidence: Comartin (Feb 2026) says people confuse CQRS with read replicas when they think about it 'purely from a scaling perspective.' The verifier found the quote supplied with this claim was spliced: in the original, 'nothing to do with scaling' refers to CQRS, not to replicas. The claim itself is consistent with the Fowler and Young definitions. Vote 3-0, but the only direct source is a practitioner blog.
  - Sources: https://codeopinion.com/read-replicas-are-not-cqrs-stop-confusing-this/, https://www.martinfowler.com/bliki/CQRS.html
- **Several authors, notably Khononov and Young, argue that the core goal of CQRS is to represent the same data with several models, and that scalability and performance are byproducts. This is contested: Microsoft's guidance puts independent scaling first.** — confidence: medium
  - Evidence: Khononov (2017): 'The goal of CQRS is to enable representation of the same data using multiple models. Not scalability, not availability... The rest is byproducts.' The Azure Architecture Center bases the pattern on reads and writes having different performance and scaling needs, and lists independent scaling as a benefit. Split vote, 2-1.
  - Sources: https://dev.to/vladikk/tackling-complexity-in-cqrs, https://learn.microsoft.com/azure/architecture/patterns/cqrs
- **CQRS is not a top-level architecture. Apply it only to the specific bounded contexts or components where it brings a clear business benefit. Many systems fit a CRUD model and should be built as CRUD, and in most systems most bounded contexts will not benefit from CQRS. Fowler says that for most systems it adds risky complexity, and that a poorly matched domain reduces productivity and increases risk.** — confidence: high
  - Evidence: Fowler: 'for most systems CQRS adds risky complexity'; 'Many systems do fit a CRUD mental model, and so should be done in that style'; 'CQRS should only be used on specific portions of a system (a BoundedContext)'. Microsoft p&p: 'you should not apply the CQRS pattern to the top level of your system'; 'the majority of bounded contexts will probably not benefit'. The current Azure guidance also says to apply it only to the parts of a system that benefit. Votes were 3-0 on all merged claims (1, 2, 3, 6). 'Most systems' is Fowler's expert opinion, not an empirical finding.
  - Sources: https://www.martinfowler.com/bliki/CQRS.html, https://learn.microsoft.com/en-us/previous-versions/msp-n-p/jj591573(v=pandp.10), https://learn.microsoft.com/azure/architecture/patterns/cqrs
- **When to use CQRS: collaborative domains, where several actors work on the same data at once, are the best indicator that it will pay off. Read-heavy workloads are also a strong case. When not to use it: simple domains or business rules, CRUD-style UI and data access that are already enough, and simple, static, non-core or non-collaborative contexts.** — confidence: high
  - Evidence: Microsoft p&p: 'Both Udi Dahan and Greg Young identify collaboration as the characteristic of a bounded context that provides the best indicator that you may see benefits'. The same guide says this is 'not a hard and fast rule' and that 'Simple, static, non-core bounded contexts are less likely to warrant the up-front investment'. Azure (updated 2026): 'might not be suitable when: The domain or the business rules are simple. A simple CRUD-style user interface and data access operations are sufficient.' Votes were 3-0 (claims 6, 7).
  - Sources: https://learn.microsoft.com/en-us/previous-versions/msp-n-p/jj591573(v=pandp.10), https://learn.microsoft.com/azure/architecture/patterns/cqrs
- **The main practical benefit is optimizing and scaling the read and write sides independently. This is especially useful when reads far outnumber writes: the read model scales out horizontally while the write model runs on fewer instances, which keeps merge conflicts down and consistency easier. Scalability alone is a weak reason to adopt CQRS in a non-collaborative domain, where adding database servers or read replicas is often enough.** — confidence: high
  - Evidence: Microsoft p&p: 'A system may process thousands of reads for every write. Segregating the two sides enables you to optimize them independently.' It also says 'Scalability should not be the only reason why you choose to implement the CQRS pattern', backed by Dahan's quote on non-collaborative domains. Azure: 'especially beneficial when the number of reads is greater than the number of writes. The read model scales horizontally... The write model runs on fewer instances.' Votes 2-1 (claim 5) and 3-0 (claim 9). The verifier suggests the wording 'especially beneficial' rather than 'most benefit'.
  - Sources: https://learn.microsoft.com/en-us/previous-versions/msp-n-p/jj591573(v=pandp.10), https://learn.microsoft.com/azure/architecture/patterns/cqrs
- **In event-driven setups, a durable log such as Kafka often carries changes between the command and query sides. This is one common way to let each side be deployed, partitioned and tuned on its own. CQRS does not require it.** — confidence: medium
  - Evidence: AxonOps: 'Kafka serves as the transport layer between command and query sides'. The independent-scaling part is the verifier's inference from standard CQRS guidance. The source page could not be fetched (DNS error), and it is vendor documentation. Split vote, 2-1.
  - Sources: https://docs.axonops.com/data-platforms/kafka/application-development/patterns/cqrs, https://learn.microsoft.com/azure/architecture/patterns/cqrs
- **Once the read and write stores are separate and the read side is updated asynchronously, the read model is eventually consistent and can serve stale data. Users may not see their own changes right away, which tends to hurt the user experience. Practitioners raise this concern often, so UX, APIs and stale-data detection have to be designed for it explicitly. Common workarounds are read-your-writes, version or offset tokens, optimistic UI and polling until the projection catches up.** — confidence: high
  - Evidence: Azure: 'the read data might not show the most recent changes immediately. This delay results in stale data... detecting and handling scenarios where a user acts on stale data requires careful consideration.' AxonOps: 'Read model lags behind write model.' Comartin (2022): eventual consistency 'Usually leads to a bad user experience' and is 'One of the most common questions I get related to CQRS & Event Sourcing'. Votes were 3-0 on all merged claims (8, 11, 18, 19). Qualification: CQRS does not force eventual consistency, because a single store or a synchronous projection can be strongly consistent.
  - Sources: https://learn.microsoft.com/azure/architecture/patterns/cqrs, https://docs.axonops.com/data-platforms/kafka/application-development/patterns/cqrs, https://codeopinion.com/?p=8411
- **The hardest implementation problem is reliably propagating each change from the command side to the query side. Options include native database replication, a queue, an event bus, an outbox with a polling publisher, an outbox with transaction-log tailing, native database streaming, and having the query side read from more than one database. Each has its own trade-offs, and two-phase commit is generally avoided. Microsoft recommends a transactional outbox with idempotent consumers to avoid dual-write inconsistencies.** — confidence: medium
  - Evidence: AWS samples page: 'how can we guarantee that one change in the command service will be guaranteed to be propagated to the query service?' It lists exactly 7 strategies and has a 'Why Not Two-Phase Commit?' section. The Azure page warns about dual writes and recommends the Transactional Outbox pattern. Vote 3-0, but the main source is secondary.
  - Sources: https://aws-samples.github.io/eda-on-aws/patterns/cqrs, https://learn.microsoft.com/azure/architecture/patterns/cqrs
- **CQRS can and should be decoupled from Event Sourcing. Projections can be built without events: with an 'is dirty' flag, by catching up on row or commit versions, or with database views. Event Sourcing is worth it only where business complexity justifies it, typically in core subdomains.** — confidence: medium
  - Evidence: Khononov (2017) lists 'Is Dirty' flags, version-based catch-up and database views ('a perfectly valid CQRS system can be implemented in the database'), and says 'employ Event Sourcing if, and only if, your business domain justifies it.' Young and Microsoft also describe CQRS without ES. Vote 3-0. The core-subdomain rule is heuristic expert guidance.
  - Sources: https://dev.to/vladikk/tackling-complexity-in-cqrs
- **In its minimal form, with separate read and write code paths over the same database, CQRS is not inherently overengineering. It keeps read-model options open, such as a materialized view, a document store or a single table. The complexity warnings mainly apply to the heavyweight form: separate stores, asynchronous projections and event sourcing.** — confidence: low
  - Evidence: Comartin (2026): 'The point is you have different code paths, so you have options'; 'So is CQRS overengineering? Not really.' Vote 3-0, but there is a single practitioner-blog source, and the verifier noted it does not say when CQRS is overkill. Read it together with Fowler's warning about complexity.
  - Sources: https://codeopinion.com/read-replicas-are-not-cqrs-stop-confusing-this/
- **Real-world example, Netflix Tudum (2025). The original design used CQRS: CMS ingestion on the editorial write path, Kafka to carry processed content, a Cassandra read store, and a Page Data Service with a per-instance near-cache refreshed per key on a schedule. Because of that eventual consistency, editors sometimes waited minutes to see changes in preview. Netflix kept the CQRS split but replaced the read path with RAW Hollow, an embedded in-memory object store that can give strong read-after-write consistency per request (it is eventually consistent by default). That removed Kafka, the external key-value store, the Page Data Service and the near-cache from the read path, and home page construction fell from about 1.4s to 0.4s.** — confidence: high
  - Evidence: ByteByteGo (Sept 2025): 'separating the "write path" for editorial tools from the "read path" for visitors'; 'editors had to sometimes wait minutes to see their changes reflected in a preview'; 'from roughly 1.4 seconds to about 0.4 seconds'. Verifiers checked this against a Netflix Tech Blog mirror (July 2025, 'from CQRS with Kafka to CQRS with RAW Hollow') and InfoQ (Aug 2025). The latency figure comes from controlled tests that left out TLS, authentication, WAF and logging overhead. Votes were 3-0 on all merged claims (13, 14, 15).
  - Sources: https://blog.bytebytego.com/p/how-netflix-tudum-supports-20-million

## Caveats
Several foundational sources are old: Fowler's bliki is from 2011 and Microsoft's CQRS Journey is 2012-2014 and archived. They are still treated as current because the guidance is definitional and architectural, and the Azure Architecture Center page (updated 2026) restates it. Statements such as 'most systems' and 'most bounded contexts' are expert opinion, not empirical data. Several claims rest only on practitioner blogs (CodeOpinion, Khononov) or vendor or secondary pages (AWS samples, AxonOps, ByteByteGo). The AxonOps page could not be fetched, so the Kafka claims were checked against other sources. The Netflix numbers come from a secondary summary, confirmed against a mirror of the primary post, and they measure controlled tests, not end-to-end production latency. Whether scalability is a primary goal of CQRS or a byproduct is contested between sources. Two claims were refuted and are left out: that CQRS means separate services, and that CQRS's complexity is mostly accidental, coming from three traps. The research did not cover adoption statistics for 2025-2026, framework or tooling trends, or quantitative comparisons with alternatives such as plain CRUD with caching, read replicas or materialized views.
